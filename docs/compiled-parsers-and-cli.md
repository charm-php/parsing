# Compiled Parsers and the CLI

`Charm\Parsing\Compiler\GrammarCompiler` turns a `Grammar` into PHP source for a
parser class. The generated class runs the grammar as ordinary method calls and
string comparisons - no clause objects, no interpreter loop. String-mode
generated parsers contain no references to this library at all.

```php
use Charm\Parsing\GrammarParser;
use Charm\Parsing\Compiler\GrammarCompiler;

$grammar = (new GrammarParser())->parse($grammarText, 'expr');

$compiler = new GrammarCompiler();
$code = $compiler->compile($grammar, 'ExprParser');

file_put_contents('ExprParser.php', $code);
```

## GrammarCompiler

```php
public function compile(Grammar $grammar, string $className, array $options = []): string
public function compileToFile(Grammar $grammar, string $className, string $filePath, array $options = []): void
```

`compileToFile()` is `compile()` plus `file_put_contents()` - it does not create
the target directory, the CLI does that.

`$options` is merged over these defaults:

| Option | Default | Effect |
|---|---|---|
| `namespace` | `null` | Emits `namespace {value};` before the class. |
| `implements` | `[]` | `implements A, B` on the class declaration. |
| `baseClass` | `null` | `extends {value}` on the class declaration. |
| `template` | `null` | Path to a template file, replacing the built-in one. |
| `globals` | `[]` | Initial `$state` of every `parse()` (`var_export`ed into the generated class; `$initialState` is merged over it). |

The goal rule is the **first rule in the grammar**: `getGoalRuleInfo()` takes the
first entry of the grammar, builds the method name from it, and uses
`$rule->getDescription() ?? $ruleName` as the description in the error message.
A grammar with no rules throws `\RuntimeException("Grammar has no rules")`.

## The generated file

`parser.template.php` expands into:

```php
/**
 * Generated parser for: {{GRAMMAR_NAME}}
 * Do not edit - regenerate from grammar source.
 *
 * Generated by Charm\Parsing\Compiler\GrammarCompiler (charm/parsing). This file is covered by the
 * Charm Parsing output exception (see LICENCE.md) and may be used under any terms.
 */
{{NAMESPACE}}
{{CLASS_DECLARATION}}
{
    private string $source;
    private int $offset;
    private int $length;
    private int $maxOffset = 0;
    private ?string $expected = null;
{{PROPERTIES}}

    /** @var array<string, string> Rule name to description mapping */
    private const DESCRIPTIONS = {{DESCRIPTIONS}};

    public function parse(string $source, array $initialState = []): mixed
    {
        $this->source = $source;
        $this->offset = 0;
        $this->length = \strlen($source);
        $this->maxOffset = 0;
        $this->expected = null;
        $this->globals = array_merge({{GLOBALS}}, $initialState);

        $result = $this->parse{{GOAL_RULE}}();

        if ($result === {{CLASS_NAME}}Signal::MISS) {
            $this->fail('{{GOAL_DESCRIPTION}}');
        }

        // Signal::HIT means success with no value - return null, like cpeg_parse()
        if ($result === {{CLASS_NAME}}Signal::HIT) {
            return null;
        }

        return $result;
    }
    ...
}

enum {{CLASS_NAME}}Signal { case HIT; case MISS; }
```

Notes on that shape:

- Every rule method returns either a value, `ExprParserSignal::HIT` (matched, no value) or
  `ExprParserSignal::MISS`. The enum is generated per class and named after it,
  so several generated parsers can live in one namespace.
- `parse()` does **not** check that the whole input was consumed. If you need
  that, end your goal rule with `$`, for example `Calc = ^ _ Expr _ $`.
- Every `parse()` starts `$state` afresh: the `globals` compile option (`[]` by default, written into the
  generated `parse()`) merged with `$initialState`. Keys a snippet set during an earlier `parse()` on the same
  instance are gone, as in the interpreted engine. `$state` is still not rolled back on backtracking.
- The header text is part of the template: generated files are covered by the
  project's output exception, not by GPL-3.0-only.

`{{DESCRIPTIONS}}` is always seeded with `'$' => 'end of input'`, followed by one
entry per rule that has a description.

### Placeholders

`compile()` replaces these with `strtr()`, so a custom template only needs the
ones it uses:

| Placeholder | Replacement |
|---|---|
| `{{GRAMMAR_NAME}}` | `$grammar->filename ?? $className` |
| `{{NAMESPACE}}` | `namespace X;` plus newline, or empty |
| `{{USE_STATEMENTS}}` | Always empty (`generateUseStatements()` returns `''`) |
| `{{CLASS_DECLARATION}}` | `class ExprParser extends Base implements A, B` |
| `{{PROPERTIES}}` | `private array $globals = ...;` |
| `{{INIT_CODE}}` | Always empty (`generateInitCode()` returns `''`) |
| `{{GOAL_RULE}}` | Goal method name, e.g. `Expr` |
| `{{GOAL_DESCRIPTION}}` | Goal description |
| `{{PARSE_METHODS}}` | All rule methods, then all snippet methods |
| `{{SIGNAL_ENUM}}` | `enum ExprParserSignal { case HIT; case MISS; }` |
| `{{CLASS_NAME}}` | The class name |
| `{{DESCRIPTIONS}}` | `var_export` of the description map |
| `{{LEXER_CLASS}}` | Fully-qualified lexer class - replaced only in token mode |

A template is read with `file_get_contents($path)`, so a missing file raises a
PHP warning and then fails on an empty template.

## One method per rule

Rule `Foo` becomes `private function parseFoo(): mixed` (the name goes through
`ucfirst(preg_replace('/[^a-zA-Z0-9]/', '_', $ruleName))`). Each method starts
with `$_offset = $this->offset;` so a snippet can report where the rule began,
and calls `$this->expect('Foo')` when the rule has a description and cannot
match empty input.

Clause code generation:

| Grammar | Generated test |
|---|---|
| `"ab"` | `\substr_compare($this->source, 'ab', $this->offset, 2) === 0` |
| `"a"` | `$this->source[$this->offset] === 'a'` (single-char fast path) |
| `/[0-9]+/` | `\preg_match('/[0-9]+/uA', $this->source, $_m, 0, $this->offset)` - `uA` is appended to the pattern from the grammar |
| `T_LNUMBER` | `$this->tokens[$this->offset] === \T_LNUMBER`, value from `$this->tokenData->getValue()` |
| `"+"` in token mode | `$this->tokens[$this->offset] === '+'` |
| `$` | `$this->offset === $this->length`, else `$this->expect('$')` |
| `^` | `$this->offset === 0` |
| `\nothing` | `Signal::HIT` |
| `@` | nothing at runtime - the sequence knows it has passed it; a later failure in that sequence calls `$this->fail($rule, true)` |
| `Foo?` | `($x !== MISS) ? $x : null` |
| `Foo+` | `do { ... } while` collecting into an array, `MISS` if empty |
| `Foo*` | same loop, empty array is a success |
| `&Foo` / `!Foo` | match, restore `$this->offset`, yield `HIT`/`MISS` |

Two branches of the generator are effectively unreachable from grammar text.
`Clause::CASE_INSENSITIVE` (modifier 16) has its own code paths in
`generateTextCode()` and in `Clause\Regex`, but `_Clause()` in `GrammarParser`
only ever sets `SPREAD`, `AND`, `NOT`, `OPTIONAL` and `REPEATING`, so no grammar
in Charm syntax switches a terminal to a case-insensitive match. Likewise
`Clause\Any` compiles to `\mb_substr(\substr($this->source, $this->offset, 4), 0, 1)`,
but a bare `.` in a grammar lexes as `T_TOKEN` and is never accepted as a clause.

Sequences save the offset, use `goto` to the end label, keep
named captures as keys (`$result['name']`), drop references to `%silent` rules,
flatten `spread:` results, and, when the sequence has no snippet, collapse an empty
result to `null` and, where `Sequence::collapses()` says exactly one element can produce a value, return
`$result[0]` instead of the one-element list (the same method the interpreter calls).

Ordered choices are compiled in one of three ways, tried in this order:

1. **Single variance point** - alternatives that differ only in one terminal
   (`Number = /hex/ {...} | /oct/ {...} | /dec/ {...}`) are merged into one
   `\preg_match()` of named groups plus an `isset()` dispatch, marked in the
   output with `// Optimized: single-variance-point pattern`.
2. **Switch dispatch** - when every alternative has known, pairwise-disjoint
   first bytes, a `switch ($this->source[$this->offset])` selects the
   alternative.
3. **Sequential** - try each alternative, restoring `$_choiceOffset` between
   them. The first alternative that does not return `MISS` wins, even if it
   matched nothing. (A commit inside an alternative needs no check here: a
   failure after it throws.)

The first two are only used when they cannot change the outcome: every
alternative must consume input (no optional, `*`, predicate or nullable
alternative), the grammar must not contain `@`, and the single-variance
optimization additionally needs the alternatives' terminals to be unable to match
at the same place whenever something follows them or a snippet decides the
result.

References to other rules are guarded at the call site when the target rule has
a minimum byte length > 0 and known first bytes (only the first byte is tested, so
that a rule that would fail further in still runs and records the failure offset):

```php
if ($this->offset >= $this->length || !\str_contains('"-0123456789[fnt{', $this->source[$this->offset])) {
    $this->expect('Value');
    $_seq1_1 = JsonParserSignal::MISS;
} else {
    $_seq1_1 = $this->parseValue();
}
```

Left-recursive rules become a Pratt pair - `parseExpr(int $_minPrec = 0)` plus
`parseExprPrimary()` - and precedence comes from `%prec`, then the `@prec`
table, then `count($alternatives) - $index`. See
[Precedence and pragmas](precedence-and-pragmas.md) for the rules and the
associativity tests (`<` for every operator - `none` groups like `left` - and
`$precedence - 1` for the right operand of a right-associative operator).

A rule in an indirect left-recursive cycle (`A = B "x" | "y"`, `B = A "z"`) gets a
`parseA()` that seed-grows around the rule body in `growA()`, with the best result so
far per offset in `$this->lrSeeds` (the property only exists when the grammar has such
a rule). The algorithm is `Rule::parse()`'s; see
[Precedence and pragmas](precedence-and-pragmas.md#left-recursion-the-short-version).

## Snippets in generated code

A snippet that contains `return` is lifted into its own private method named
after the registry entry `Grammar` assigns (`{RuleName}_{n}`):

```php
private function snippet_Pair_1($_offset, $_p0, $_p1, $_p2, $_p3, $_p4, $_p5)
{
    $state = &$this->globals;
     return [$_p0 => $_p5];
}
```

- `$_offset` is the rule's start offset and is only passed when the snippet
  contains `return`.
- `$_p0`, `$_p1`, ... are the positional values the sequence produced;
  `$_context['name']` becomes the matching named parameter, or a plain local
  variable of the same name when there is nothing bound to it.
- `$state` is an alias of `$this->globals` - an array, not a
  `Charm\Parsing\State`. Methods like `$state->getToken()` do not exist here.
- Snippets without `return` are inlined as a single statement.

A snippet's return value is recognised by class (`Charm\Parsing\SequenceIgnore`,
`SequenceResume`) and by enum case name (`MISS`), so the library does not have to
be loaded: `$MISS` or `\Charm\Parsing\Signal::MISS` fails the sequence,
`SequenceIgnore` ends it as a valueless success and `SequenceResume` carries on.
Anything a snippet throws is rethrown as `Charm\Parsing\Error\SnippetError` when
that class exists. Control flow is otherwise driven by the class's own
`{ClassName}Signal` enum.

A clause type the compiler does not know emits
`$_result = false; // Unknown clause type: {class}`, so unusual grammars fail
rather than crash at compile time.

## Errors

Generated parsers throw their own `{ClassName}ParseError`, emitted into the same file next to the
`{ClassName}Signal` enum (so the parser stays standalone). It extends `\RuntimeException`, so
`catch (\RuntimeException)` works, and carries the details as readonly properties:

```php
class JsonParserParseError extends \RuntimeException
{
    public readonly bool $committed;   // a commit (`@`) had been passed: no alternative could recover
    public readonly int $sourceLine;   // 1-based (`line` is taken by \Exception)
    public readonly int $sourceColumn; // 1-based, in bytes
    public readonly int $offset;       // byte offset of the failure
    public readonly string $expected;
    public readonly string $found;     // 'x', \xNN or "end of input"
}
```

`fail()` computes the values and throws it:

```php
private function fail(string $expected, bool $committed = false): never
{
    ...
    throw new JsonParserParseError("Parse error at line {$line}, column {$col}: expected {$expected}, found {$found}", $committed, $line, $col, $offset, $expected, $found);
}
```

Every terminal that fails records the offset it failed at and what it expected
(`$maxOffset`, `$expected`: the distinct things expected at that offset, joined with " or "), so the message points at the deepest failure rather than the goal
rule and lists every alternative that was possible there; the description of a described rule stands for the
terminals inside it (`$shield`), with the same line and column the interpreter reports. `$found` is the character in single
quotes, `\xNN` for non-printable bytes, or `end of input`. Line and column are
recomputed from the source on failure. See
[Errors and debugging](errors-and-debugging.md).

## Token-mode generated parsers

With `@lexer` in the grammar, `compile()` picks `parser-token.template.php`,
which adds two properties and a lexer call:

```php
private array $tokens;
private \Charm\Parsing\TokensInterface $tokenData;

public function parse(string $source, array $initialState = []): mixed
{
    // Tokenize input using the lexer
    $lexer = new {{LEXER_CLASS}}();
    $this->tokenData = $lexer->lex($source);
    $this->tokens = $this->tokenData->getTokensArray();
    ...
    $this->length = \count($this->tokens);
```

`$this->offset` is now a token index, and `fail()` converts it to a byte offset
with `$this->tokenData->getOffset($offset)` and describes the offending token
with `describe($offset)`.

Because of `\Charm\Parsing\TokensInterface` and the lexer call, token-mode
generated parsers are **not** standalone: the library (and for `PhpLexer`,
`nikic/php-parser`) must be autoloadable at runtime. See
[Token mode](token-mode.md).

## The charm-compile CLI

`bin/charm-compile` is installed by Composer as `vendor/bin/charm-compile`.

```
charm-compile <grammar-file> [options]
charm-compile - [options]              Read grammar from stdin
```

| Flag | Long | Meaning |
|---|---|---|
| `-o` | `--output <file>` | Write here instead of stdout; missing directories are created with `mkdir($dir, 0755, true)`. |
| `-c` | `--class <name>` | Class name. |
| `-n` | `--namespace <ns>` | `namespace` compile option. |
| `-e` | `--extends <class>` | `baseClass` compile option. |
| `-i` | `--implements <a,b>` | `implements` compile option, comma separated. |
| `-t` | `--template <file>` | `template` compile option. |
| `-T` | `--target <target>` | `php` (default), `c`, `js` or `python`. The other targets generate a standalone C99, Node.js (CommonJS) or Python 3 parser that returns the same tree, from a grammar without snippets or with [portable snippets](../REFERENCE.md#portable-snippets). `-c` is the C identifier prefix; `-o x.c` also writes `x.h`. Everything about them is in [Portable targets](../REFERENCE.md#portable-targets-c-javascript-python). |
| `-q` | `--quiet` | Suppress the progress lines on stderr. |
| `-h` | `--help` | Print usage and exit 0. |

There is no flag for the `globals` compile option - set it through the PHP API.

Behaviour worth knowing:

- The class name defaults to `ucfirst(preg_replace('/[^a-zA-Z0-9]/', '', $name)) . 'Parser'`
  where `$name` is the input filename with `.peg` and `.grammar` stripped
  (`expr.peg` becomes `ExprParser`). It is then validated against
  `/^[a-zA-Z_][a-zA-Z0-9_]*$/`; a bad name exits 1 with
  `Error: Invalid class name: ...`.
- With `-o` the PHP code goes to the file and status messages
  (`Parsing grammar...`, `Compiling to class 'ExprParser'...`,
  `Written to: ...`, `Generated 41234 bytes.`) go to stderr, so
  `charm-compile expr.peg -c ExprParser` can be redirected safely.
- Missing input file, empty stdin, a grammar that fails to parse
  (`Error parsing grammar: ...`) or a compile failure
  (`Error compiling grammar: ...`) each print to stderr and exit 1. Running
  without a grammar file prints the help text and exits 1.
- The grammar is parsed with `new GrammarParser()`, which does not run
  `GrammarPreprocessor`. Template rules (`List<Item>`) are only expanded by
  `cpeg_parse()` / `cpeg_create()`; on the command line they are a parse error.

```bash
vendor/bin/charm-compile expr.peg -o src/ExprParser.php -c ExprParser -n "App\\Parser"
cat grammar.peg | vendor/bin/charm-compile - -c MyParser -q > MyParser.php
```

The example grammars use the `.cpeg` suffix, which the CLI does not strip, so
pass `-c` or the class becomes `JsoncpegParser`. A grammar that uses template
rules - `example-grammars/es3.cpeg` has `List<T, Sep>` - cannot be handed to the
CLI at all, because the templates need expanding first:

```php
use Charm\Parsing\GrammarPreprocessor;
use Charm\Parsing\GrammarParser;
use Charm\Parsing\Compiler\GrammarCompiler;

$text = (new GrammarPreprocessor())->process(file_get_contents('example-grammars/json.cpeg'));
$grammar = (new GrammarParser())->parse($text, 'json');
(new GrammarCompiler())->compileToFile($grammar, 'JsonParser', 'src/JsonParser.php', [
    'namespace' => 'App\\Parser',
    'globals' => ['depth' => 0],
]);
```

`example-grammars/php/` shows the other direction: `php.cpeg` is compiled with a
project-supplied template, `charm-compile php.cpeg -t php-parser.template.php`.
That template starts from `parser-token.template.php` and adds
`use PhpParser\...` imports plus helper methods (`attributes()`, `init()`) that
its snippets call.

`cpeg_create()` honours the `CHARM_COMPILED` environment variable: when it is
set, the grammar is compiled and `eval('?>' . $code)`d as
`CompiledParser_{n}_{hash}` instead of being interpreted. That is the quick way
to check that a grammar compiles to the behaviour you expect. See
[Getting started](getting-started.md).

## Portable targets

`charm-compile --target=c|js|python` does not use `GrammarCompiler`. `Charm\Parsing\Compiler\Portable\Program` lowers the grammar to
integer tables (the decisions the PHP compiler makes from the grammar - collapse, spread depth, precedence, first bytes of a rule -
are made once, there), `RegexCompiler` turns each regex into bytecode, and `CGenerator`, `JsGenerator` and `PythonGenerator` write the tables
into a file that also contains the engine (`src/Compiler/Portable/runtime/`). The engine implements the semantics of the PHP compiled parser, and
`charm-tests/support/targets.php` runs every conformance row through it. See [REFERENCE.md](../REFERENCE.md#portable-targets-c-javascript-python).

## Grammar optimizers

`Charm\Parsing\Optimizer\OptimizerPipeline` rewrites a grammar before it is
interpreted or compiled:

```php
use Charm\Parsing\Optimizer\{OptimizerPipeline, ConsecutiveTerminalsOptimizer};

$pipeline = new OptimizerPipeline([new ConsecutiveTerminalsOptimizer()]);
$grammar = $pipeline->optimize($grammar);
```

`add()`, `prepend()` and `getOptimizers()` manage the list; optimizers run in
order and each receives the output of the previous one.
`ConsecutiveTerminalsOptimizer` merges runs of two or more adjacent, unnamed,
unmodified `Text`/`Regex` alternatives into one regex
(`"break" | "case" | "catch"` becomes `/(?:break|case|catch)/`) and reports the
count through `getMergeCount()`. It implements
`Optimizer\GrammarOptimizerInterface::optimize(Grammar $grammar): Grammar`, and
replaces rule clauses in place.

## Choosing the engine

Compile when parse time matters or when you ship a parser without the library; develop with the
interpreter. On a realistic grammar (the [SQL tutorial's](tutorial-sql.md#step-15-compiling-the-grammar))
compiled parsing takes about a sixth of the time. What changes the speed of a compiled parser - regexes
the compiler cannot analyse, `@`, parsing an operand twice - is listed in the
[reference](../REFERENCE.md#performance).

## Benchmarks

`php benchmarks/run.php [grammar|json|expression|expr-eval|all]` runs the suite;
`php benchmarks/expression-eval-benchmark.php "description"` appends a table to
`benchmarks/expression-parser.log` (`--no-log` skips the write, `--optimize`
turns on `ConsecutiveTerminalsOptimizer`).

From the run recorded in `benchmarks/json-parser.log` as "Commit semantics
implemented (JIT)" (2026-01-21 12:12:11, PHP 8.5.1 with JIT, parses per second):

| Input | `json_decode` | Compiled | Interpreted |
|---|---|---|---|
| string | 6,822,855 | 882,411 | 83,901 |
| number | 6,652,150 | 707,364 | 80,102 |
| array | 2,150,950 | 115,462 | 14,689 |
| object | 2,143,649 | 142,091 | 20,056 |
| nested | 780,694 | 40,800 | 6,706 |

In that run the compiled parsers were 6.1 to 10.5 times faster than the
interpreted engine, and `json_decode` was 7.7 to 19.1 times faster than the
compiled parser. The last run in
`benchmarks/expression-parser.log` (2026-01-22 10:05:48, PHP 8.5.1, average over
1000 iterations of each of twelve expressions) reports 0.0716 ms interpreted,
0.0141 ms compiled and 0.0024 ms for SQLite evaluating the same arithmetic.

## Checked-in generated parsers

`src/Library/JsonParser.php` and `src/Library/JsExpressionParser.php` are
compiler output kept in the repository (namespace `Charm\Parsing\Library`). They
were produced by an earlier compiler build - they throw a plain `\RuntimeException`
instead of a generated `{Class}ParseError`, predate the commit and precedence fixes of 0.1.2,
and their header comment lacks the output-exception line - so treat the templates in
`src/Compiler/` as the reference and regenerate before relying on them.
